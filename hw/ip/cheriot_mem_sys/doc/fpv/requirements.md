# CHERIoT memory subsystem FPV requirements

This page lists what the CHERIoT memory subsystem must do, one testable requirement per row.

* Each row gives the requirement, its sources, and the checks that decide it.
* A row with the mark (*RTL*) holds a rule that no specification states.
  The rule follows the design's present behaviour.
* A mark that names a part, as in "(*RTL*: the bit order of the tags within a meta word)", applies to that part only.
* A value that the top sets is written as its parameter ([Parameters](#parameters)).
* The [FPV testplan](README.md#how-the-plan-fits-together) shows how the requirements, the testpoints and the checks fit together.

## Terms

A term that only one group uses is defined in that group.

| Term | Meaning |
|---|---|
| CHERIoT mode | The mode enable `cheriot_ena_i` is exactly `MuBi4True`. Any other value, an invalid encoding included, is ePMP mode ([Block Diagram](../theory_of_operation.md#block-diagram), [Revocation Engine](../theory_of_operation.md#revocation-engine); [cheriot_mem_sys.hjson `INTERSIG.MUBI`](../../data/cheriot_mem_sys.hjson)). |
| Tag path | The path that stores and returns the tags: the core's tag filter, the WTRC, the 2:1 tag arbiter and the RMW filter, up to the meta SRAM. |
| Tag sideband | The capability tag carried next to `cored_tl_d`: `cored_tag_h2d` with a request and `cored_tag_d2h` with a response, each a `mubi4_t` ([Block Diagram](../theory_of_operation.md#block-diagram)). A request's tag sideband is set when it is exactly `MuBi4True`. Any other value, `MuBi4False` or an invalid encoding (neither `MuBi4True` nor `MuBi4False`), is clear ([Block Diagram](../theory_of_operation.md#block-diagram)). |
| Hinted capability load | A read of both words of a capability with the tag sideband set, which asks for the tag ([load_store_unit.rst, Data-Side Memory Interface](../../../../vendor/lowrisc_ibex/doc/03_reference/load_store_unit.rst)). |
| W0, W1 | The lower and the upper 32-bit word of a capability. The core sends W0 first ([Write-to-Read-and-Compare Filter (WTRC)](../theory_of_operation.md#write-to-read-and-compare-filter-wtrc)). |
| Capability store to the NVM | A write in CHERIoT mode to the NVM with the tag sideband set ([Write-to-Read-and-Compare Filter (WTRC)](../theory_of_operation.md#write-to-read-and-compare-filter-wtrc)). The WTRC handles it. |
| Sweep | One run of the revocation engine over `TBRE_NUM_CAPS` capabilities from `TBRE_BASE_ADDR` ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| Watch window | For one capability of a sweep: from the engine presenting the read of its lower word until its clear is presented. A core write in it keeps its tag ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| `fatal_fault` | The subsystem's one fatal alert ([Security Alerts](../interfaces.md#security-alerts)). |
| Meta request | A request the tag filter sends on its meta port, to read or to write one tag. |
| Device port, host port, meta port | The three ports of a tag filter. The tag filter receives requests on its device port. It forwards the data half of each access towards memory on its host port, and it sends its meta requests on its meta port. The core's tag filter has `cored_tl_d` as its device port and `cored_tl_h` as its host port. The engine's tag filter has `tbre_tl_h` as its host port. |
| Meta answer | The answer that a tag filter receives on its meta port to a meta request. |
| Lookup | The meta request that a tag filter sends to read the tag of an access. |
| Meta word | A 32-bit word of the meta SRAM. |
| Bit select | The sideband of a meta request that names the bit of the tag within its meta word ([RMW Filter](../theory_of_operation.md#rmw-filter)). |
| Operation | A request that the RMW filter accepted, from its acceptance until its answer is taken. |
| Write-back | The full-word write that the RMW filter sends to the meta word that it has read, with only the addressed tag changed. |
| Fault input | A signal on which a block of the subsystem reports a fault to the alert logic, which then requests `fatal_fault`. |
| Requester ports | The four ports that reach the meta SRAM: the tag port (from the RMW filter), `corerevbm_tl` (bitmap reads from the core's TRVK filter), `revbm_tl_d` (software, through `xbar_main`) and the engine's bitmap port, on which the revocation engine's TRVK filter reads the bitmap ([Block Diagram](../theory_of_operation.md#block-diagram), [Meta SRAM Address Map](../theory_of_operation.md#meta-sram-address-map), [Access Checkers](../theory_of_operation.md#access-checkers), [Timing](../theory_of_operation.md#timing)). |
| Region of a port | The tag port owns both capability tag regions, the NVM capability tags and the main SRAM capability tags, `0x1100_0C00`-`0x1100_97FF`. The other three requester ports own the revocation bitmap, `0x1100_0000`-`0x1100_0BFF` ([Meta SRAM Address Map](../theory_of_operation.md#meta-sram-address-map), column "Reachable from"). |
| Legal request | All four conditions of [Access Checkers](../theory_of_operation.md#access-checkers) hold: CHERIoT mode; the address inside the port's region; a full 32-bit word at a word-aligned address (`a_size` = 2, so TL-UL sets all four `a_mask` bits: [Request Channel (Channel A)](../../../tlul/doc/TlulProtocolChecker.md#request-channel-channel-a), `sizeMatchesMask`); the opcode `Get` or `PutFullData`. |
| Source ID on `meta_sram_tl` | The 4:1 arbiter shifts the `a_source` of a request left by two bits and puts the number of the requester port in the two lowest bits. It shifts these bits off again on the `d_source` of the answer ([Usage of Source and Sink ID Bits](../../../tlul/README.md#usage-of-source-and-sink-id-bits), [Source ID growth](../../../tlul/README.md#source-id-growth)). |
| Takes an answer | A port takes an answer when it accepts the answer with `d_ready`. |
| Base | The lowest address a capability covers, decoded from its address and its bounds fields (CHERIoT architecture specification v1.0, section 7.13.3 (PDF pages 69-70)). |
| Sealing capability | A capability whose permissions are in the sealing format and grant SE, US or U0, the capabilities that the instruction CLC exempts (the CHERIoT architecture specification v1.0, CLC, PDF page 114). The base of a sealing capability is in a namespace of its own, so such a capability is never revoked (CHERIoT architecture specification v1.0, section 7.8 (PDF page 58)). |
| Revocation bit of a base | Bit `b` of bitmap word `w`, with `w * 32 + b` = (base - `MainSramBaseAddr`) / 8 ([Meta SRAM Address Map](../theory_of_operation.md#meta-sram-address-map)). The engine uses the bit of the capability's base, not of its address ([Revocation Engine](../theory_of_operation.md#revocation-engine); CHERIoT architecture specification v1.0, section 7.8 (PDF page 58)). For example, base `0x1000_4000` is word 64, bit 0. |
| BASE, NUM | The values of `TBRE_BASE_ADDR` and `TBRE_NUM_CAPS` at the start. |
| Swept capabilities | The N capabilities at BASE, BASE + 8,..., with N = min(NUM, (top - BASE) / 8) and top the `MainSramTopAddr` or `NvmTopAddr` of BASE's region ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| Active | `TBRE_REGWEN` is 0 ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| Revoked | A swept capability whose tag is set, which is not a sealing capability, whose base lies in the main SRAM region, and whose base's revocation bit is set or whose bitmap lookup failed ([Revocation Engine](../theory_of_operation.md#revocation-engine); [Revoking Capabilities](../programmers_guide.md#revoking-capabilities)). |
| Touches | A core write touches a capability when it is presented on `cored_tl_d`, or accepted there and not yet answered, with its address in the capability's 8 bytes ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| Clear | The write of tag 0 that the engine presents, through its tag filter, for a revoked capability ([Revocation Engine](../theory_of_operation.md#revocation-engine)). |
| Tracked capability | One swept capability that the formal tool chooses freely at the start of a sweep. Any swept capability can be chosen, so a check on the tracked capability covers every swept capability. |
| Fatal state | The time from the first failed request or raised fault input after reset until the next reset. |

## Parameters

The instantiation of the block sets the values below, and they differ from one chip to the next.
The requirements name each value by its parameter, so the same rows hold for every instantiation.

| Parameter | Meaning | Value on Earl Grey |
|---|---|---|
| `MainSramBaseAddr` | Base address of the main SRAM region, inclusive. | `0x1000_0000` |
| `MainSramTopAddr` | Top address of the main SRAM region, exclusive. | `0x1003_0000` |
| `NvmBaseAddr` | Base address of the NVM region, inclusive. | `0x3000_0000` |
| `NvmTopAddr` | Top address of the NVM region, exclusive. | `0x3020_0000` |
| `MetaSramBaseAddr` | Base address of the unified meta SRAM. | `0x1100_0000` |
| `MemSizeRevbm` | Size of the `revbm` window in bytes, set by topgen. Must equal the size of the main SRAM revocation bitmap, which an assertion in the RTL checks. | `3072` |
| `AlertAsyncOn` | Adds synchronizers to the alert sender for an alert handler on another clock, set by topgen. | `1'b1` |
| `AlertSkewCycles` | Cycles of skew tolerated on the differential alert signals, set by topgen. | `1` |

## Tag filter

The group is security-relevant ([Groups](#groups)).

Conditions:

* Every row holds for each access that the core presents, except a capability store to the NVM.
* The [WTRC](#wtrc) group covers a capability store to the NVM.
* For the upper word of a capability whose tag sideband has an invalid encoding, the theory of operation states two tags.
* The checks of the tag leave that word out, and the plan page lists the case under Out of scope.

| Term of this group | Meaning |
|---|---|
| Tagged region | The main SRAM, from `MainSramBaseAddr` up to `MainSramTopAddr`, or the NVM, from `NvmBaseAddr` up to `NvmTopAddr`: the memory that can hold capabilities ([Meta SRAM Address Map](../theory_of_operation.md#meta-sram-address-map)). |
| Captured tag | The tag a W0 load returns, held by the tag filter for the W1 load that follows ([Tag Filter](../theory_of_operation.md#tag-filter)). |

Testpoints: [`tf_forward`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_forward) (V1, priority 1), [`tf_lookup`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_lookup) (V1, priority 1), [`tf_meta_request`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_meta_request) (V1, priority 1), [`tf_sticky_tag`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_sticky_tag) (V1, priority 1), [`tf_errors`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_errors) (V2S, priority 2), [`tf_flow`](../../data/cheriot_mem_sys_fpv_testplan.hjson#tf_flow) (V2, priority 2).

## WTRC

The group is security-relevant ([Groups](#groups)).

Conditions:

* The rows apply to a capability store to the NVM and to the requests around it.
* Every other access passes the WTRC unchanged, and the [Tag filter](#tag-filter) rows cover it with the WTRC in place.
* The WTRC tracks the capability being stored, and it treats a word as out of sequence in four cases ([Write-to-Read-and-Compare Filter (WTRC)](../theory_of_operation.md#write-to-read-and-compare-filter-wtrc)).
* Case 1: a W1 arrives while the WTRC tracks no capability.
* Case 2: after a W0, any request arrives that is not the W1 of the same capability.
* Case 3: any request arrives after a W1 and before that W1 is answered or its tag write is issued.
* Case 4: after the tag write of a W1 is issued, a W1 arrives, or a W0 arrives before that W1 is answered.
* A word is matched when its NVM read succeeded, it is a full-word `PutFullData` in sequence, and its data and data integrity equal those of the NVM answer ([Write-to-Read-and-Compare Filter (WTRC)](../theory_of_operation.md#write-to-read-and-compare-filter-wtrc)).
* The checks decide the rows on a faulty word for every faulty word, also after an earlier one.

| Term of this group | Meaning |
|---|---|
| Faulty word | A word of a capability store to the NVM that is out of sequence or partial, that carries a bad command or data integrity, or whose NVM answer has a bad response integrity. |
| Owed tag write | The tag write of a capability store to the NVM is owed from the cycle in which the NVM answer of W1 arrives, when W0 and W1 both matched, until the meta port accepts the tag write. |

## Registers and alert

The group is security-relevant ([Groups](#groups)).

Conditions:

* A row that says a cause raises `fatal_fault` requires an alert event on `alert_tx_o`: a full handshake on the alert pair and the acknowledge pair of the alert handler ([Differential Alert Signaling](../../../../top_earlgrey/ip_autogen/alert_handler/doc/theory_of_operation.md#differential-alert-signaling)).
* The alert rows hold outside the alert handler's in-band reset ([Employed Solution](../../../../top_earlgrey/ip_autogen/alert_handler/doc/theory_of_operation.md#employed-solution)).
* A "failed request" is a request whose command integrity code does not match, or a write whose data integrity code does not match ([Usage of User Bits](../../../tlul/README.md#usage-of-user-bits)).
* No document says whether the data integrity code of a read is checked, so no row covers a read whose only mismatch is that code.
* A request has an "illegal combination of address, size and mask" when its size is greater than 2, or when its mask has a bit set on an inactive lane ([Explicit Error Cases](../../../tlul/README.md#explicit-error-cases)).
* A `PutFullData` request also has an illegal combination when its mask has a 0 on an active lane.
* `AlertLat` is the number of cycles that the environment allows from a cause, an alert test or a ping to its alert event.
* No specification gives this number.
* The [Start, status and interrupt](#start-status-and-interrupt) group holds the rows of the fields that hardware writes.
